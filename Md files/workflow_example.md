# Dynamic Agent Workflow: Step-by-Step Example

To understand how the **Dynamic Agent Orchestrator** works, let's trace a real example through its pipeline. 

### The Example Prompt
Imagine a user submits the following prompt via the Streamlit UI:
> *"Research average global smartphone adoption rates by region, analyze which regions are growing fastest, compute simple percentage comparisons, and write the results to a markdown report file."*

Here is exactly how the system orchestrates this request, step by step:

---

### Step 1: Goal Intake (`goal_intake_node`)
The system doesn't just pass the prompt directly to an agent. First, the `Goal Intake` stage uses an LLM to parse the raw text into a structured `Goal` object. 

* **What happens:** It identifies the title, description, constraints, assumptions, and specific deliverables. 
* **In our example:** 
  * **Title:** Global Smartphone Adoption Analysis
  * **Deliverables:** A markdown report detailing adoption rates, fastest-growing regions, and percentage comparisons.
  * *Note: If the prompt is too vague (e.g., "do some research"), the node marks `needs_clarification=True` and the pipeline pauses to ask the user for more details.*

### Step 2: Planning / Task Graph Generation (`task_graph_node`)
The orchestrator now acts as a project manager. It looks at the structured Goal and the list of available agents in the registry (Researcher, Data Analyst, Document Generator) and breaks the work down into a **Directed Acyclic Graph (DAG)** of tasks.

* **What happens:** It creates a sequence of tasks and establishes dependencies to ensure they run in the correct order.
* **In our example:** It generates three tasks:
  1. **Task A (Capability: Researcher):** Search the web for global smartphone adoption rates by region. *(Dependencies: None)*
  2. **Task B (Capability: Data Analyst):** Analyze the research from Task A to find fastest-growing regions and compute comparisons. *(Dependencies: Task A)*
  3. **Task C (Capability: Document Generator):** Compile the analysis from Task B into a final `report.md` file. *(Dependencies: Task B)*

### Step 3: Execution Engine & Scheduling (`execution_engine_node`)
The Execution Engine is the heart of the loop. It scans the Task Graph to find tasks that are "ready" to run (i.e., tasks that have no pending dependencies).

* **What happens:** Since Task B and Task C depend on upstream work, they are blocked. Only **Task A** is ready. The engine marks Task A as `running`.

### Step 4: Agent Resolution & Execution (`agent_resolution_node`)
The system maps the ready task to the correct AI persona and executes it.

* **What happens:** 
  * The system sees Task A requires a `Researcher`.
  * It spawns the **Researcher Agent**, equipping it with its specific system prompt and allowed tools (e.g., `web_search`).
  * The agent runs in a loop, searching the web, gathering data, and eventually returning a factual summary of smartphone adoption rates.

### Step 5: Evaluation (`evaluator_node`)
Once the agent finishes, the Evaluator checks the result. 

* **What happens:** 
  * If the Researcher successfully returns the data, Task A is marked as `success`.
  * The loop circles back to **Step 3 (Execution Engine)**. Now that Task A is complete, its dependent, **Task B (Data Analyst)**, is unblocked and marked as ready.
  * Task B is resolved to the **Data Analyst Agent**, which uses the `python_repl` tool to compute percentage comparisons.
  * This cycle repeats until **Task C (Document Generator)** writes the final markdown file.

### Step 6: Replanning (If things go wrong)
What if the Researcher in Task A fails to find good data because the search API timed out? 
* The Evaluator marks Task A as `failed`.
* Instead of crashing, the workflow routes to the **Replanner (`replanner_node`)**.
* The Replanner modifies the task graph (e.g., adding a task to try a different search query) and sends the pipeline back to the Execution Engine. It can retry until it hits a configured limit (`Config.MAX_REPLANS`).

### Step 7: Result Assembly (`result_assembly_node`)
Once all tasks in the DAG are marked as `success`, the workflow ends.

* **What happens:** The system gathers the outputs of the final tasks (in this case, the markdown report generated by Task C), saves everything to the `backend/data/runs/` folder, and surfaces the final success message and report to the user in the Streamlit chat UI.
